PHẢN XẠ 1 GIÂY

3. MẸO PHẢN XẠ "1 GIÂY" (Liếc 1 từ trên Đề → Khóa 1 từ dưới Đáp Án)

A. Custom Tag & Phương thức vòng đời

  • 🔑 Thấy đề có doStartTag → Tìm ngay đáp án có EVAL_BODY_INCLUDE (hoặc SKIP_BODY).
  • 🔑 Thấy đề có doEndTag → Tìm ngay đáp án có EVAL_PAGE (hoặc SKIP_PAGE).
💡 Câu thần chú: "Start thì Body, End thì Page".

B. JDBC (Database)

  • 🔑 Đề có chữ stored procedures → Chọn ngay CallableStatement (Câu #334).
  • 🔑 Đề có PreparedStatement (ưu điểm/lợi ích) → Chọn đáp án có chữ precompiled hoặc parameter (?) hoặc Both A and B.
  • 🔑 Đề hỏi phương thức trả về ResultSet → executeQuery().
  • 🔑 Đề hỏi phương thức trả về số dòng dạng số nguyên int → executeUpdate().

C. JSP Scope & Đối tượng ngầm định (Implicit Objects)

  • 🔑 Đề hỏi is NOT a scope → Chọn ngay response (hoặc out). (Nhớ: chỉ có đúng 4 scope: page, request, session, application).
  • 🔑 Đề hỏi default scope của <jsp:useBean> → Chọn ngay page.
  • 🔑 Đề hỏi đối tượng ngầm định chỉ dùng được khi isErrorPage="true" → Chọn ngay exception.

D. Thư mục WAR & Cấu hình web.xml

  • 🔑 Thấy WEB-INF/lib → Chứa file thư viện .jar.
  • 🔑 Thấy WEB-INF/classes → Chứa file mã nguồn biên dịch .class (Servlets).
  • 🔑 Đề hỏi tham số chung cho toàn bộ ứng dụng (shared by all / entire web app) → Chọn ServletContext / thẻ <context-param>.
  • 🔑 Đề hỏi cấu hình riêng cho 1 Servlet duy nhất (single servlet) → Chọn ServletConfig / thẻ <init-param>.

E. Kiến trúc MVC & HTTP Method

  • 🔑 Đề hỏi NOT a component of MVC → Chọn ngay Database (hoặc Service Layer).
  • 🔑 Đề hỏi NOT an HTTP method → Chọn ngay UPDATE (vì UPDATE là câu lệnh của SQL!).
  • 🔑 Phân vai MVC: Controller = Servlet, View = JSP, Model = JavaBean / POJO / DAO.

F. Phân biệt Forward vs SendRedirect

  • 🔑 <jsp:forward> / RequestDispatcher.forward(): Chuyển tiếp bên trong Server, giữ nguyên URL trên thanh địa chỉ, chỉ tốn 1 request, giữ nguyên dữ liệu trong request scope.
  • 🔑 response.sendRedirect(): Chuyển hướng phía Client (trình duyệt gửi request thứ 2 mới hoàn toàn), đổi URL trên thanh địa chỉ, mã trạng thái là SC_MOVED_TEMPORARILY (302).

0% ĐÚNG Khẳng định "Exhaustive testing is possible"

Trong nguyên lý ISTQB, kiểm thử vét cạn mọi trường hợp là bất khả thi (impractical and impossible). Khẳng định nó khả thi luôn luôn là câu sai (Câu #5, #31, #116).

0% ĐÚNG "The black box tester should understand source code"

Black-box tester chỉ quan tâm đến input/output và tài liệu đặc tả chức năng, không cần biết hay đọc mã nguồn bên trong (Câu #32).

0% ĐÚNG "Static testing requires the running of tests through the code"

Static testing (Review / Inspection / Static Analysis) là kiểm thử tĩnh trên tài liệu và mã nguồn, tuyệt đối không chạy chương trình (Câu #357).

Gần như 0% Phương án đứng trơ trọi System testing, Walkthrough, Usability

Các từ đơn lẻ đứng một mình trong câu hỏi lựa chọn thường là phương án mồi nhử (System testing: 0/5, Walkthrough: 0/4, Usability: 0/4).

PHẢN XẠ 1 GIÂY

3. MẸO PHẢN XẠ "1 GIÂY" (Liếc 1 từ trên Đề → Khóa 1 từ dưới Đáp Án)

A. Phân loại Kỹ thuật Kiểm thử (Test Techniques)

  • 🔑 Đề hỏi NOT a black box testing technique → Chọn ngay Decision testing (Câu #28 - vì Decision testing là White-box!).
  • 🔑 Đề hỏi NOT a white box technique → Chọn ngay Boundary value analysis (Câu #36 - vì BVA là Black-box!).
  • 🔑 Đề có tester's skills, intuition and experience hoặc Error guessing → Chọn ngay Experience-based (Câu #92, #96).
  • 🔑 Đề có Cyclomatic Complexity thuộc phương pháp nào → Chọn ngay White box (Câu #108).
  • 🔑 Công thức Cyclomatic Complexity với L (edges), N (nodes), P (components) → Chọn L - N + 2P (Câu #216).
  • 🔑 Tên gọi khác của White Box Techniques → Structural Testing (Câu #160).

B. Phân biệt các cặp khái niệm kinh điển

  • 🔑 Re-testing (Confirmation testing) vs Regression testing:
    • Re-testing: Chạy lại test case để xác nhận lỗi đã được sửa thành công (Câu #332).
    • Regression: Phát hiện lỗi phát sinh ngoài ý muốn ở vùng code cũ không sửa (unexpected side effects) (Câu #350).
    • Công cụ tự động hóa kiểm thử hồi quy → Record/Playback hoặc Capture/Playback (Câu #65, #71).
  • 🔑 Verification vs Validation:
    • Verification: "Are we building the product right?" (Đúng quy cách/đặc tả) → True (Câu #7).
    • Validation: "Are we building the right product?" (Đúng nhu cầu người dùng).
  • 🔑 Severity vs Priority:
    • Severity: Mức độ ảnh hưởng kỹ thuật của lỗi lên hệ thống (impact of defect on system) (Câu #67, #278).
    • Priority: Thứ tự ưu tiên cần phải sửa lỗi trước hay sau (order in which defects should be fixed) (Câu #278).
  • 🔑 Inspection vs Walkthrough:
    • Inspection: Do Moderator chủ trì, có quy trình chính thức chặt chẽ (Câu #82, #279).
    • Walkthrough: Do Author (tác giả tài liệu) chủ trì, đào tạo và lấy góp ý (Câu #254, #279).

C. Các vai trò trong buổi Review (Review Roles)

  • 🔑 Người chịu trách nhiệm ghi chép biên bản, ghi nhận toàn bộ lỗi & câu hỏi mở (document all issues, problems and open points) → Chọn Scribe (hoặc Recorder) (Câu #98).
  • 🔑 Người lập kế hoạch, điều phối buổi họp và hòa giải giữa các bên (mediates between people) → Chọn Moderator (Câu #129, #148).

D. 7 Nguyên lý Kiểm thử ISTQB (7 Principles)

  • 🔑 Exhaustive testing is impossible: Không thể test hết mọi trường hợp → phải tập trung dựa trên rủi ro và độ ưu tiên (use risks and priorities) (Câu #5, #31, #116, #329).
  • 🔑 Pesticide Paradox (Nghịch lý thuốc trừ sâu): Lặp lại mãi một bộ test case sẽ ít tìm ra lỗi mới → Same tests over time detect fewer issues (Câu #255).
  • 🔑 Context dependent: Kiểm thử phụ thuộc vào ngữ cảnh → Testing approaches should vary based on the specific context (Câu #250).

E. Kỹ thuật thiết kế Black-box

  • 🔑 Đề có different combinations of inputs to result in different outputs → Chọn ngay Decision table testing (Câu #90).
  • 🔑 Đề có changes in state within an application → Chọn ngay State transition testing (Câu #252).
  • 🔑 Đề có process flows related to typical use of the system → Chọn ngay Use case testing (Câu #239).
  • 🔑 Đề có valid and invalid partitions hoặc achieve input and output coverage → Chọn ngay Equivalence partitioning (Câu #56, #311, #324).
  • 🔑 Mục tiêu chính của Acceptance Testing trên phần mềm thương mại COTS → To build confidence in the application (Câu #315 - xây dựng niềm tin để nghiệm thu).

F. Mức độ kiểm thử & Chiến lược tích hợp

  • 🔑 Đề hỏi NOT part of system testing → Chọn ngay Top-down integration testing (Câu #37 - vì Integration testing thuộc mức riêng trước System testing).
  • 🔑 Tích hợp Big-bang → Integration of all components at once without prior testing (Câu #269).
  • 🔑 Công cụ giả lập module gọi cấp trên dùng trong Bottom-up → Driver (còn gọi là Test harness / Scaffolding) (Câu #3, #167).
  • 🔑 Kiểm thử hệ thống (System Testing) cần điều tra cả: Non-functional requirements and Functional requirements (Câu #343).
